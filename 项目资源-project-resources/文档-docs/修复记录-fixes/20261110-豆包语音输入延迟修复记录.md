# 20261110-豆包语音输入延迟修复记录

## 问题现象

- 用户使用 VoiceKey 1.11.0，豆包渠道、边说边上屏，按住右 Option 说话、松开结束，仍感觉比豆包输入法慢。
- 当前是长按模式，点按模式的 1.5 秒静音停止设置不构成本次原因。
- 用户已关闭胶囊实时文字，保留直接向光标处输入的方式。

## 调研过程

- 以 `J3n5en/voicekey` 的 `v1.11.0` 为基线，提交 `f9ca4a0af5db3d7a493a6d0ccb4ae7d1a467d869`，分支 `codex/doubao-latency`。
- 程序已有按键按下时预热入口，但豆包引擎未实现预热。原来要到长按开始识别后才建立连接并完成任务、会话握手。
- 握手期间录到的语音会积压，原来补发也只按实时速度发送，连接造成的落后会延续到录音结束。
- 没有更改两遍识别、标点、语音拒绝等识别参数，也没有切换服务、代理或本地模型。

## 修复方案

1. 在原有按键预热入口准备豆包连接与任务；真正开始识别时才创建识别会话、发送语音。
2. 预热任务只消费一次，闲置 15 秒后释放；设备失效时清除旧任务；连接准备最多等待 10 秒。
3. 继续保留原来的 200 毫秒起音静音。仅豆包渠道在存在积压时按已有重放流程使用的 4 倍速度补发，追上后恢复实时速度，不删除音频帧。
4. 将发送节奏拆成独立文件，并在结束时取消后台发送任务，避免闲置任务残留。
5. 添加固定文件测速工具 `vk-latency`，不打开麦克风、不触发键盘输入、不修改用户配置。
6. 本机完整构建遇到上游离线模块使用未稳定的 `vdotq_s32`。改为对应的同一条 `sdot` 指令，并用有符号整数的逐项结果比对验证，保持原有计算结果与硬件加速。

- 固定每 20 毫秒的绝对采集时刻，避免测速程序自身睡眠累计误差。

## 后续注意

- 这是本机、少量固定语音的对照结果，网络与豆包服务端响应仍会波动。初期基线测试也出现过一次连接超时，不能据本轮成功断言已消除云端故障。
- 没有使用系统键盘事件脚本，也未声称已验证真实麦克风输入至目标文本框的端到端耗时；用户选择自行试用快捷键。
- 该优化保留原有边说边上屏流程，未修改用户的胶囊偏好、后处理设置和全局代理。
- 更新官方版本可能覆盖本机优化，升级前需重新检查上游是否已经包含相应修复。
